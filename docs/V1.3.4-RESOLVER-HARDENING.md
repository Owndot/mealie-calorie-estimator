# v1.3.4 resolver-hardening audit

Prepared against v1.3.3 (`dff1ef8`), on `fix/v1.3.4-resolver-hardening`.
The changes preserve judge provenance, bound concurrent recipe pipelines, and correct judge cache
identity. They do not change match acceptance, generate consensus nutrients, or deploy anything.
A wrong nutrient assignment remains worse than an unresolved ingredient.

## Evidence and limits

The production counts and OFF examples come from the supplied audit: 20 recipes, 266 ingredient
rows, 255 matched and 11 unresolved. The v1.3.3 release was verified through GitHub. Local
investigation used the bundled BLS 4.0 and USDA databases, actual provider lookups and their
cache-independent `poolOnly` diagnostic path. No production recipe, token, cache or server was
accessed or modified. OFF production searches were not replayed; their observed outcomes are
reported as supplied, not as newly measured live results.

The audit does not include the complete Bandnudeln classifier/query payload or the exact OFF
shortlist. Its exact historical candidate set cannot be reconstructed from the summary alone.
The reproducible alternatives below explain where the resolver can diverge.

## A. Judge provenance: fixed

`resolveNutrients` previously returned `null` after an ambiguous/none/invalid judge outcome when
its deterministic result was null. With `LLM_NUTRIENT_ENABLED=false`, that is the normal unresolved
case. The metadata existed in the resolver's local `provenance` object and logs but was discarded
by `deterministic === null ? null : { ...deterministic, judge: ... }`.

There were additional losses: the low-confidence branch had the same null return, the nutrient
sanity rejection returned the deterministic result without metadata, and the estimator's unmatched
branch copied only a newly computed `judgeTrigger`. This explains the observed replacement of
`gate-suppressed-pool` by `no-database-record` and the seven missing decision fields.

The estimator now uses `resolveNutrientsWithDiagnostics`. Its result can carry `match: null` and
the existing `ResolvedNutrients["judge"]` type. The original match-only resolver contract remains
unchanged for override previews and other callers. A single field mapping feeds matched and
unmatched provenance. Actual judge triggers take precedence over recomputed eligibility.

Selected, ambiguous, none and cached decisions retain trigger, verdict, reason, candidate count,
pool fingerprint, model and prompt version. Invalid replies and operational failures keep the
existing null-verdict convention, with their reason and other audit fields populated. A rejected
selection keeps the model's `selected` verdict but prefixes its reason with the confidence/sanity
rejection; `matched: false` and null provider/nutrients distinguish it from an accepted match.
When generation is enabled, a retained generated fallback likewise keeps the judge audit.

No invocation means decision fields stay null. `judgeTrigger` may still express eligibility,
which is an existing schema convention. `llmParticipated` now includes judge usage, including
cached decisions, so the recipe's LLM ingredient list no longer omits that participation.

## B. Generic pasta and equivalent retail records: investigated, deferred

Generic composition records already exist, including BLS `E401000`, “Teigwaren eifrei, roh”
(346 kcal/100 g), and USDA `168927`/`169736`, dry pasta (371 kcal/100 g). Existence alone does not
establish egg content, grain source or preparation state for a particular input.

With structured/canonical German `Bandnudeln`, English `wide noodles`, unknown state/form,
`processed_single_food` and category `pasta`:

- German core `Nudeln` activates the existing `Nudeln` → `Teigwaren` lemma synonym. BLS accepts
  `E401000` at confidence 0.85; the resolver would return before invoking the judge.
- German core `Bandnudeln`, English core `noodles` does not activate that exact lemma synonym.
  Both providers miss deterministic acceptance. A separate `poolOnly` pass returns 25 survivors.
  The top local shortlist includes rice noodles (score 10), egg noodles (7), BLS rice noodles
  (about −3.67), and cooked/soba/somen variants. USDA's floor is 30; BLS's is 50. This is not a
  pool of interchangeable generic wheat pasta records.
- Once the chain misses, the resolver builds the local shortlist, computes OFF proxy/last-resort
  eligibility, filters retail hits, rebuilds the shortlist with reserved retail places and asks
  the judge. A plain ingredient has no property-bearing local record under this routing test,
  so OFF last-resort can run even when low-scoring local survivors exist. The supplied production
  audit reports the judge declining multiple equally plausible retail products.

The appropriate next investigation is validated generic identity retrieval/classification, before
retail consensus. Do not relax the core gate merely because a food name ends in “nudeln”.

Consensus is outside this patch. `ProviderMatch` represents one real record, and `JudgeDecision`
selects one offered ID. The current shortlist deduplicates by folded name plus energy and truncates
its population; it cannot prove independent manufacturers, full-population dispersion or the
absence of excluded outliers. Missing form/category evidence also cannot establish equivalence.
An aggregate would require source-list provenance, a nutrient aggregation/missing-value policy,
and explicit generic-estimate semantics throughout the calculator and cache.

For a future benchmark, evaluate dispersion per nutrient using a median and MAD, with a separate
maximum-deviation guard so an isolated outlier cannot hide behind a tight majority. Near-zero
nutrients need absolute tolerances; sodium matters for sauces and broths. Require explicit food
identity and state agreement, sufficient independent sources, and no brand/property requirement.
No numerical acceptance thresholds are claimed validated here. The audit's 351–366 kcal pasta
cluster merits investigation; a 3–192 kcal mixed-state set must fail regardless of its median.

## C. Prepared broth versus concentrate: investigated, deferred

For the supplied `processed_single_food` / `broth` / unknown-state classification, local evidence is:

| Record | kcal/100 g | Current behavior |
|---|---:|---|
| BLS `X416243`, Gemüsebrühe | 4 | Rejected by the composite-dish food-type gate |
| USDA `171583`, Soup, vegetable broth, ready to serve | 5 | Rejected by the same food-type gate |
| BLS `R821000`, Gemüse Bouillon/Brühe/Suppe (Brühwürfel, Pulver) | 195 | Survives into the diagnostic pool at score −5; not accepted |

The broth probe used German core `Brühe` and English core `broth`; the latter is supplied by the
audit, while the complete German classifier payload is unavailable. The composite-dish rejection
of prepared broth follows directly from the supplied food type and stored record types.

`FoodState` supports raw/cooked/dried/unknown. `FoodForm` supports whole/ground/powder/leaf/seed/
flakes/paste/unknown. Preservation supports fresh/dried/canned/frozen/unknown. Name inference can
recognize powder and paste; derived-product identity also recognizes broth and concentrate.
There is no complete ready-to-consume/reconstituted/cube/concentration axis. OFF filtering uses
reported energy, name identity, excluded category tags and measured fat for numeric requests;
name-derived state/form/preservation and a limited category summary reach the judge. It is not a
complete preparation-state validator, and OFF label nutrition can describe a prepared serving.

The normalizer receives structured food names and unit names. Grams are calculated separately
from quantity/unit conversion, density/piece tables or a gram estimate. The nutrient resolver gets
neither quantity nor unit nor recipe preparation instructions. `originalText` and free-text notes
are deliberately not used. `750 g`, particularly estimated grams, cannot safely select a prepared
record. Future work should first reconcile food-type taxonomy for ingredient broths and represent
explicit preparation/dilution evidence across providers, rather than exempting broth from gates.

## D. True ambiguity: preserved

Generic coriander still lacks leaf-versus-seed evidence; explicit fresh coriander retains USDA
`169997`. Generic thyme still lacks fresh-versus-dried evidence. Generic protein powder does not
identify its source/formulation. Spice blends, pink peppercorns and Utskho Suneli receive no invented
records. Hoisin and rice vinegar get no special cases or arbitrary brand selection. No acceptance
changes are made for these foods; an existing valid resolution can still stand when its own
structured evidence and provider records justify it.

## E. Concurrent recalculation: fixed at the shared pipeline boundary

Estimate and webhook handlers used `setImmediate` to start each request independently. Backfill
was sequential within one invocation but shared no global capacity limit. There was no job queue.
Each estimate processes ingredients sequentially, but many recipes multiplied concurrent work:

- Classification is batched per recipe; classifier/reranker/gram calls use the shared LLM rate
  limiter. The judge uses its own timed fetch and currently bypasses that per-minute limiter.
- OFF ordinary and judge searches share OFF's limiter, retries and User-Agent.
- Mealie reads/writes have request timeouts but no shared concurrency bound or write retries.
- The recipe-name index can be built redundantly on concurrent misses; it has no in-flight
  coalescing. Database initialization reuses promises; cache operations use synchronous SQL.js
  with debounced persistence. These are not a recipe-job scheduler.

`runEstimationPipeline` now schedules the entire operation, before the first recipe read through
the final write, through one `EstimationQueue`. `ESTIMATION_CONCURRENCY=2` is the conservative
process-local default. A non-positive, fractional, non-finite or unsafe integer fails startup.
The startup log reports the configured limit; Compose passes it through.

The oldest runnable job gets a free slot. The same recipe slug is serialized, while unrelated
slugs can proceed. Per-request `force` and `overrideManual` options are copied when enqueued,
not combined or promoted across requests. Every job re-reads the recipe after acquiring its slot
and reuses existing manual-ownership checks. Errors reject only that job and release its slot and
slug lock. No automatic retries are added, particularly around uncertain write outcomes.

HTTP 202 and response bodies remain unchanged. It still means accepted, not completed. This limits
active work, not total pending memory: the waiting queue is in-memory, has no capacity rejection or
status endpoint, and is lost on restart. Shutdown does not drain it. Multiple replicas have separate
limits and locks; this is not a distributed lock. Read-only override previews bypass the pipeline.
These are explicit limits, not a durable job-delivery guarantee. Recipe-index coalescing and a shared
judge per-minute budget remain possible separate improvements.

## OFF logging and polyols: unchanged

The routing expression remains proxy, then last-resort, then null; `offQueried` remains
`offRoute !== null`. Existing route logging and shared-label Hoisin regressions pass. OFF's rate
limiting, retries, product fetching and User-Agent code are unchanged.

The v1.3.3 real erythritol zero-energy fixture, polyol subtraction/clamping, other sugar-alcohol
factors and ordinary macro-energy checks remain covered by the full suite. Neither nutrient
extraction nor sanity-check arithmetic changes in this patch.

## Leerdammer confidence: policy explained, acceptance unchanged

Ordinary OFF matching ranks names, brand and nutrition completeness after semantic rejection.
`MIN_ACCEPTABLE_SCORE` is 30, and confidence is `min(0.95, score / 100)`. A 0.53 match is therefore
accepted under existing thresholds. The shared judge deliberately does not replace accepted real
records. Brand evidence must originate in the structured name; matching brand similarity adds 25
points, while a differing reported brand subtracts 15 rather than acting as a universal hard veto.
An exact complete branded label has a separate priority path, but a `fuzzy` match does not prove
that exact-label path was taken.

This explains the reported behavior; 0.53 is not a calibrated probability or proof of exact product
identity. The audit's nutrient values alone cannot establish identity. No new arbitrary confidence
threshold is justified by this one example. A future branded-policy benchmark should require
positive brand/variant agreement, reject explicit contradictory brands/variants, and route remaining
identity ambiguity to review regardless of nutrient plausibility. Test synthetic matching/missing/
conflicting brand labels and variant contradictions before changing thresholds or provider caches.
This patch pins the existing accepted-OFF fast path with a synthetic 0.53 fixture.

## Completeness: unchanged

Withholding uses unresolved known mass fraction greater than 30%, or no resolved ingredients.
It does not estimate the unknown ingredient's energy. This conservatively withholds a recipe with
750 g unresolved broth even if a prepared interpretation would contribute few calories. Assuming
low energy first would silently discard the concentrated interpretation. Unknown-gram ingredients
are not included in the known-mass denominator, an existing limitation. No broth exemption or
energy-based materiality heuristic is introduced.

## Compatibility, migration and risks

No Mealie schema change, provenance field rename, production migration or manual cache deletion.
Old provenance cannot be recovered retrospectively from stored nulls; a new estimate populates it.
Only judge cache identity advances from `j1` to `j2`; provider and classification caches remain.
A fresh judge call may therefore produce a different valid verdict than a previously cached call.
Matching rules and prompt instructions themselves are unchanged.

`LLM_NUTRIENT_ENABLED=false` remains fully supported and is exercised by the new provenance tests.
The package stays at 1.3.3 pending the repository's separate release process. No release/tag,
production change or main-branch push is part of this work. The original untracked `.claude/` and
`bench/` directories are unrelated and untouched.

A lower concurrency trades bulk latency for stability. Slow/time-limited services still occupy a
slot, and request failures remain possible. Repeated forced requests execute serially rather than
being deduplicated: no options are silently discarded, but repeated requests can produce repeated
writes after fresh reads. Manual-edit races from external clients and multiple engine processes
are not solved by a process-local queue.

## Production validation after an approved deployment

1. Build/smoke the Docker image in CI; deploy only through the normal approved release process.
   Keep `LLM_NUTRIENT_ENABLED=false` and start with `ESTIMATION_CONCURRENCY=2`.
2. Confirm the startup concurrency/judge flags. Force one known matched recipe and one ambiguous
   recipe; compare judge logs with the final seven provenance fields, including a repeated cached
   decision. Invalid requests must retain failure reasons without acquiring nutrients.
3. Run the 19-recipe recalculation batch, wait for completion logs/writebacks, and verify at most
   two active recipe pipelines per process. Check per-recipe failures explicitly; 202 is not success.
   Retry failed recipes individually only after inspecting any uncertain writeback outcome.
4. Compare provider IDs and nutrients for existing resolved ingredients, including zero-kcal
   erythritol and fresh coriander. Verify generic coriander/thyme, ambiguous formulations and
   unresolved broth still do not acquire arbitrary records. Confirm withheld totals remain null.
5. Verify OFF route logs and unchanged User-Agent/rate behavior. Review changed judge decisions
   after the cache version bump. Compare completion/error rates and elapsed bulk time, rather than
   treating a higher match rate as the success criterion.
